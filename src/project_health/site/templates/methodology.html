This site publishes metrics only — no scores, no verdicts, and no judgment on whether a number is good or bad (DECISIONS.md D25, D29). Every metric shows its own definition, population, and window next to it; where a CHAOSS Knowledge Base definition exists, that metric links it directly. Each metric also carries a tier:

TierMeaning
establishedWidely used in CHAOSS and/or peer-reviewed literature, with a standard formula.
proxyA defensible stand-in for something not directly observable (e.g. "reviewer" from a commit-trailer convention).
experimentalMathematically well-defined, not yet validated for this project.
classifiedDerived from classifying message text (Phase 2 only; preliminary — see below).

Full principles: DECISIONS.md D1 (phasing) and the project's own METRICS.md conventions (§0).

Preliminary. Published ahead of PMC review and production calibration of the classification cutoffs (D26, D27) — read the method below, and judge accordingly.
  • Pinned classifier model: {{ model_id }} — never -latest; a model change is a versioned recompute.
  • Thread sampling: up to K={{ sample_k }} threads per venue-quarter stratum, seeded (seed={{ sample_seed }}) for reproducibility.
  • Message-level labels map to one of 7 intensity tiers (−2 closing/positive … 4 attack); thread-level outcomes (escalation, resolution, abandonment) are derived deterministically from those tiers, never judged by the model directly.

  • Public-benchmark results against six human-labeled datasets: docs/benchmark/public-v1.md — strong ground truth for personal_attack/hostility/sarcasm, partial or none for the rest.
  • Not yet covered: GitHub PR comments and ASF Slack (Phase 2a/2b scope).

Every number on this site comes from a plain script, never an LLM at runtime (the pinned classifier above is the one exception — its output is cached by input hash, so re-rendering never calls the model again; D22).

{% endcall %} {% call sections.section("known-limitations", "Known limitations", None) %}
  • Identity resolution. Two raw identifiers (a git email, a GitHub login, a JIRA username) merge automatically only on a mechanical, high-confidence match (exact email, the GitHub-noreply pattern); everything else needs a human-reviewed identity_overrides.yaml entry and stays as separate, unresolved identities until then.
  • Sampling and small-n. Classified metrics rest on a stratified sample (see Conversation patterns above); every rate/ratio/concentration/latency metric also carries its own minimum-sample floor (METRICS.md §0.6) — below it, the site shows "insufficient data" rather than an unstable number.
  • GitHub-only vs. JIRA review. GitHub-PR-specific metrics (e.g. PR time to first review) see only the review activity that happened on GitHub, a subset of Cassandra's JIRA-centric review process — reported as a separate, narrower companion to the git-trailer/JIRA-reviewer-field proxy metrics, never merged with them.
  • Partial peer collection. A peer project's GitHub-PR backfill can span several weekly runs; /peers/ shows "Collecting — N of 3 passes complete" rather than a number that looks final while that's in progress.
